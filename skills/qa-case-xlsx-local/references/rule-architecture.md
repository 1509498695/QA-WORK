# qa-case-xlsx 独立规则与交付架构

## 当前状态

- 实现状态：`implemented_local_verified`。
- 目标架构：独立、本地、离线优先。
- 源目录：`D:\project\work\skills\qa-case-xlsx-local`。
- 运行依赖：Codex bundled 文档/PDF/表格运行时；不依赖任何业务工作区。
- 正式规则包：50 条，发布版本 `20260814.2`，稳定 ID，不自动从历史用例学习。

## 数据流

```text
本地源文件
  -> source_packet + evidence ledger
  -> source_facts
  -> generation_blueprint + GR-01..08 matrix
  -> immutable base cases
  -> classification + triggered rule evaluations
  -> candidate cases
  -> final cases + mapping ledger
  -> local readiness
  -> offline template workbook
  -> exact readback + visual preview
```

每一层都是显式 JSON 产物，使用相同的 `run_id`、`input_sha256` 和 `rule_release_version`。禁止跨任务拼接产物。

## 来源层

`source_packet.json` 负责证明“读了哪些文件和哪些可见内容”。它不负责决定业务事实。文件 SHA-256 与逐文件 `source_id` 是后续追溯根。

`source_evidence_ledger.json` 负责图片、PDF 页面渲染和嵌入对象。视觉证据必须有 `review_status`，不能用“已提取”代替“已查看”。

`source_facts.json` 负责事实与冲突：

- confirmed：来源足以支持；
- pending：来源不足、视觉未复核或互相冲突；
- conflicts：同主题互斥值的显式集合。

外链、未读项和默认排除项都留在来源层，不进入事实推断。

## 通用生成核心

通用核心来自原 qa-case 的可移植部分：

- 需求事实到蓝图的结构化；
- GR-01～GR-08 完整性矩阵；
- 基线用例与需求定位；
- 业务分类、对象域、横向标签和项目路由；
- 等价类、边界值、状态、异常、恢复和关联回归；
- 原子拆分、静态合并和人话化；
- 候选到最终的可校验映射。

未合并任何外部系统能力：在线文档、项目平台、代码查询、知识库、工作区任务状态和在线交付。

## 正式规则包

### 维度

- business：8 个主业务分类；
- object：6 个常见业务对象域；
- horizontal：15 个横向风险维度；
- style：4 个个人表达与拆分维度；
- project：现有 CoD/SAMO 正式规则。

正式规则总数固定为 50。ROK、Beagle、Dobe 的项目风险矩阵保存在独立项目参考中，不改变这 50 条稳定规则的 ID 和数量。

### 发布包

`references/rules/` 只允许包含：

- `rule-index.json`；
- 索引路由到的正式规则 JSON；
- `release-manifest.json`。

不允许候选 JSONL、在线证据索引、历史版本目录、失败载体 token 或自动学习日志。

`release-manifest.json` 对索引和每个正式规则文件记录 SHA-256。运行时先校验再加载；任一文件变化但清单未更新即失败。

`references/rules/*.json` 是按原始字节发布并校验的不可变构件，必须通过 `.gitattributes` 禁止换行规范化，确保克隆、迁移和重新检出后仍得到相同 SHA-256。

### 触发

规则必须满足证据触发：

- 当前事实或蓝图出现规则触发条件；
- 规则评估记录 `applicable`、`not_applicable` 或 `pending`；
- applicable 规则必须映射到候选；
- 候选声明的横向/项目规则必须有对应 applicable 评估。

禁止因“通常要测”而无证据批量套用，禁止跨维度笛卡尔积。

## 离线迁移谱系

当前 50 条规则来自用户已确认的个人用例规则包。独立化时保留规则 ID、语义、修订号和确认信息，删除在线载体 ID、候选学习文件和证据索引；每条规则改为引用本文件中的稳定语义锚点。该迁移不等于重新从外部资料推导规则。

## 八类定义边界

系统、商业化、养成、技能、副本、玩法、活动和赛季按主要业务验证目标互斥选择；对象域与横向标签独立附加，不用来替代主分类。

## 界面展示与交互控件

只有来源出现可见界面或可操作控件时触发。检查内容、可见/禁用状态、点击反馈和状态变化，不凭规则补造入口或按钮。

## 提醒红点与新手引导

红点和引导必须有来源证据才触发；分别验证出现条件、消除条件、顺序、中断和恢复，不默认所有功能都有红点或引导。

## 时间刷新与状态流转

来源出现开放期、刷新点、倒计时或生命周期时，按时间前、边界点、时间后以及初始、进行中、完成、失效状态拆分。

## 数据计算、资源奖励与边界限制

计算、奖励和边界分别建立可判定目标。使用来源给出的公式和值；规则只提示最小、最大、临界、空值、容量和到账位置等测试维度。

## 存储持久化、同步一致性与异常恢复

只有业务结果对重进、重登、切换作用域或失败恢复可见时触发。普通用例观察玩家可见状态，不以缓存、落库或内部日志为主要结果。

## 重复幂等、权限资格与本地化兼容

重复操作、资格矩阵、语言/地区/平台差异都必须由当前来源触发，只选择会改变预期结果的最小组合。

## 原子粒度与字段表达

状态、角色、对象、时序或主要预期改变时拆分；同状态同操作下的静态展示项可合并。字段职责遵循 `humanization.md`。

## 人话表达与技术术语降噪

最终用例写游戏内名称、测试动作和可观察结果；代码名、接口、协议、缓存、日志和埋点留在审计分析，不进入 A:J 的普通业务表达。

## 备注白名单与交付状态

备注默认留空，只允许待确认、环境限制、跨部门协助、复测说明。任何待确认或未完整读取状态都会把根工作簿降为草稿。

## 通用检查模块口径

通用检查是独立一级模块，位于全部业务模块之后；二级模块使用界面与适配、时间与刷新、异常与恢复等实际检查分类，不使用“常规测试点”等历史别名。

## CoD/SAMO 基础项目规则

CoD/SAMO 正式项目规则只在当前源包出现服务器/地区/平台、英雄军团、城市地图、联盟多人、活动赛季或商业化机制时触发。

## CoD/SAMO 扩展项目规则

扩展规则遵循最小组合，不对服务器、地区、平台、语言、活动阶段、角色和对象做全排列；动态表现只有明确证据时触发。

## 项目路由

项目识别来自用户本次说明或源包明确别名。未知项目使用 generic。项目参考只补高风险维度，不补业务事实。

优先级：

1. 用户本次明确事实；
2. 当前源包事实；
3. 内置项目参考；
4. 50 条个人正式规则。

若项目参考与源包冲突，以源包为准；若源包内部冲突，必须 pending。

## 模块

- 最终模块必须是玩家/测试人员可理解的业务模块。
- 禁止使用“协议”“接口”“客户端模块”“服务端模块”等技术分组。
- 通用检查使用独立一级模块 `通用检查`，并连续放在业务用例之后。
- SAMO 可使用内置模块快照；无法唯一映射时登记 provisional 并转草稿。

## 映射账本

每条最终用例都必须回溯到候选，每条候选都必须有去向。允许：

- retained：1 -> 1；
- rewritten：1 -> 1；
- split：1 -> N，N >= 2；
- merged：N -> 1，N >= 2；
- not_applicable：1/N -> 0，必须写具体理由。

映射记录包含候选 ID、最终 ID、规则 ID、原因和证据定位。语义签名用于阻止同义重复和无记录改写。

## 正式与草稿

### 阻断生成

- 没有 confirmed 业务事实；
- 没有可建立的原子测试目标；
- 规则包、基础流水线或模板损坏；
- 工作簿无法回读。

### 草稿

存在任一项：

- 源文件 `partial` 或 `unreadable`；
- 视觉证据未完成复核；
- 来源冲突；
- 事实、蓝图、完整性矩阵或项目分类 pending。

文件名：`<需求名>-测试用例-待确认草稿.xlsx`。

### 正式

所有来源和视觉证据完成读取，冲突清零，所有关键状态已确认，流水线和工作簿门禁通过，`pending=0`。

文件名：`<需求名>-测试用例.xlsx`。

## 工作簿

- 使用 `assets/local-case-template.xlsx`；
- 单 Sheet：`测试用例`；
- A:J 固定十列；
- 第 1～8 行为蓝色标题、DRI、本地来源、用例总数和结果统计，不展示审计元数据；
- 第 9～10 行为表头区；
- 第 11 行开始为用例；
- D2 为用例总数；I3:I6 为 P/F/D/N/A 统计；I7/I8 为执行率/通过率；
- 冻结第 10 行，不创建 Excel Table 或筛选表主题；
- 只合并连续相同的 B 列一级模块，以及同一一级模块内连续相同的 C 列二级模块；D:J 正文不合并；
- 优先级和测试结果使用下拉校验；
- 长文本换行，步骤保留真实换行；
- 不含宏、外部连接、在线 URL、图片列或嵌入证据。

## 审计与验收

工作簿生成后必须：

1. 重新导入；
2. 对比 A:J 全部用例值；
3. 核对双层表头、顶部与模块合并、D:J 无合并、公式、冻结窗格和零 Excel Table；
4. 扫描公式错误；
5. 渲染预览并视觉检查；
6. 将结果写入 `workbook_readback.json`。

发布前还需完成：结构校验、50 条规则校验、单元测试、六类源文件夹具、QAWORK 外运行、离线运行、安装目录逐文件哈希一致。

## 变更治理

- 规则内容变化必须提高 `rule_revision`、给出原因并重建清单。
- 规则新增/删除会改变 50 条契约，必须重新与用户确认。
- 不在运行过程中自动写回正式规则。
- 源码由 `D:\project\work` 的 QA Skill Hub 根仓库版本化；没有用户明确授权时不 push，不以远端名称改变 Skill 身份。

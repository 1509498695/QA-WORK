# 用例人话化与字段职责

## 基本原则

- 写玩家或测试人员能执行、能观察、能判断的内容。
- 不把实现细节、代码类名、接口、协议、缓存、落库、日志或埋点当作普通业务用例的主要观察对象。
- 不写“功能正常”“显示正常”“符合配置”“操作成功”等无法判定的空话。
- 同一术语在整份工作簿中保持一致；优先采用源包原词。

## A:J 字段职责

- 用例编号：按最终顺序从 1 连续编号。
- 一级模块：业务功能或独立的“通用检查”。
- 二级模块：具体流程/状态/对象/检查分类；“通用检查”下必须给具体二级模块。
- 检查点：一句话说明“对象 + 条件/状态 + 要验证的结果”。
- 前置条件：只写执行前已经成立的状态，不写准备过程，不引用其他用例。
- 操作步骤：逐行 `1. 动作` 连续编号；一行一个动作。
- 预期结果：对应操作后可直接观察的确定结果，必要时逐条对应步骤。
- 优先级：仅 `P0`、`P1`、`P2`。
- 测试结果：初始为空，执行时只填 `P`、`F`、`D`、`N/A`。
- 备注：默认空；仅使用 `待确认`、`环境限制`、`跨部门协助`、`复测说明` 前缀。

## 模块顺序

1. 按玩家主流程或业务生命周期排列业务模块。
2. 同一模块内按正常 → 边界 → 异常/恢复 → 回归排列。
3. `通用检查` 作为独立一级模块，连续放在全部业务用例之后。

## 优先级

- P0：核心入口、主流程、关键资格、关键结算、不可逆资源/付费风险。
- P1：重要分支、状态切换、边界、异常恢复、主要关联回归。
- P2：低风险表现、弱影响兼容和辅助提示。

优先级由业务影响和发生概率共同决定，不能因为用例来自通用规则就统一降为 P2。

## 草稿表达

待确认内容优先进入审计产物，不强行写成正式用例。若已确认部分可以形成用例，工作簿保持可执行，根文件名标记“待确认草稿”；备注只在某条已生成用例确实受该待确认项影响时使用。

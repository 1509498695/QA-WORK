# 通用测试用例生成蓝图

## 目的

先把源包事实转成稳定蓝图，再应用个人规则。这样可以区分“策划案说了什么”和“测试设计补了什么”，并保证最终用例可追溯。

## 蓝图节点

每个 `blueprint_node` 对应一个主要业务验证目标，至少记录：

- `blueprint_node_id`；
- 标题与业务目标；
- 角色/对象；
- 入口、资格和前置状态；
- 触发动作与主流程；
- 目标状态和可观察结果；
- 数据、数量、时间、范围或配置边界；
- 失败、中断、恢复、重复操作；
- 关联模块和旧玩法回归基线；
- `source_refs`；
- `status`：`confirmed` 或 `pending`。

业务目标不同就拆节点。一个节点可以产生多条用例，但一条用例只能有一个主要验证目标。

## GR-01～GR-08 完整性矩阵

| ID | 维度 | 必查内容 |
|---|---|---|
| GR-01 | 主流程与闭环 | 入口、操作、成功结果、退出/完成 |
| GR-02 | 权限资格与对象 | 角色、等级、资源、次数、对象类型、允许/禁止集合 |
| GR-03 | 状态与生命周期 | 初始、进行中、完成、失效、切换、重登/重进后的状态 |
| GR-04 | 数据计算与边界 | 最小/最大/临界值、空值、数量、公式、累计、刷新 |
| GR-05 | 异常恢复与幂等 | 失败、取消、中断、重试、重复点击、重复领取、断线恢复 |
| GR-06 | 界面交互与表现 | 文案、图标、按钮态、红点、遮挡、适配、反馈、引导 |
| GR-07 | 关联模块与回归 | 上下游入口、库存/邮件/排行/记录、旧玩法、共享状态 |
| GR-08 | 时效范围与兼容 | 开关、时间边界、服务器/地区/平台/语言/版本范围 |

每项状态只能为：

- `covered`：已在蓝图或用例中覆盖，并给出来源/规则定位；
- `not_applicable`：当前需求明确不涉及，并写具体原因；
- `pending`：来源不足、冲突或尚未读完。

不允许用“已考虑”“常规检查”代替证据。任一 `pending` 都会把交付模式降为草稿。

## 基线用例

`base_cases.json` 是从已确认蓝图直接得到的不可变基线。每条包含：

- `base_case_id`；
- 主蓝图节点与相关节点；
- `source_refs`；
- 检查点、前置条件、步骤、预期和优先级；
- 基于上述内容的 `content_sha256`。

个人规则不能修改基线；它们只能在候选层保留、重写、拆分、合并或标记不适用，并在映射账本记录原因。

## 分类与路由

每个蓝图节点选择唯一主业务分类：

- `system`：持续性系统能力、入口、开关、长期状态；
- `commercialization`：礼包、购买、付费、商品、权益；
- `growth`：养成、升级、升星、解锁、成长资源；
- `skill`：技能触发、目标、效果、冷却、叠加；
- `instance`：副本/战斗实例的进入、过程、结算、退出；
- `gameplay`：互动循环和规则玩法；
- `activity`：有明确开放周期和阶段的活动；
- `season`：赛季框架、阶段继承、重置和范围。

对象域与横向标签可以多选，但不能替代主业务分类。项目模块只用于最终分组，不决定事实。

## 原子拆分

以下任一变化通常需要拆分：

- 角色或资格不同；
- 初始/进行中/结束/失效状态不同；
- 正常、失败、取消、中断、恢复路径不同；
- 允许与禁止对象集合不同；
- 时间前、边界点、时间后不同；
- 预期结果需要分别观察才能判定。

以下内容可以合并：同一状态、同一入口、同一操作下的一组静态文案/图标/排版检查，且失败定位不会变模糊。

## 候选到最终

- `retained`：基线语义和表达均可直接保留；
- `rewritten`：语义不变，仅按字段职责和人话表达重写；
- `split`：一个候选拆成多个独立目标；
- `merged`：多个同状态静态目标合成一条；
- `not_applicable`：给出具体事实理由，不得只写“不适用”。

所有候选必须有基线或正式规则来源；所有最终用例必须有候选映射；所有候选必须有去向。

## 旧玩法回归

- 当前源包明确描述旧行为：可以建立回归节点并引用当前源包。
- 当前源包只说“沿用/复用/参考旧玩法”：记录 `旧玩法基线缺口`，不得猜入口、流程、数值或结算。
- 用户另外上传旧策划案：作为同一源包中的独立来源处理，冲突仍按源包冲突治理。

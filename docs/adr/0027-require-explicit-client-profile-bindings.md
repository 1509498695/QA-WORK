# 客户端默认无 Profile 权限并要求用户显式绑定

执行客户端完成 ADR 0026 的管理员登记后，默认不能查看、枚举或使用任何 Provider Profile，也不能仅凭有效客户端证书申请飞书短期访问令牌。授权控制面必须为确定的 `tenant_ref`、`client_ref` 和 `profile_ref` 建立显式客户端 Profile 绑定，且绑定只能由该 Profile 对应的已验证飞书用户按 ADR 0029 在授权控制面浏览器页面中批准。

客户端 Profile 绑定表示该用户允许一个确定执行客户端在 ADR 0028 明确批准的语义能力范围内为该 Profile 申请短期访问令牌租约。管理员批准客户端只表示该设备或安装实例可以连接授权控制面，不能代替用户委托、自动绑定管理员本人或为客户端开放同租户其他 Profile。每个客户端与 Profile 组合独立绑定和撤销；一个客户端使用多个 Profile、或一个 Profile 用于多个客户端时，都必须分别产生可审计的绑定关系。

绑定不构成 OAuth Scope 授予，也不构成任何一次正式写入授权。令牌租约仍须同时满足租户准入、客户端有效、绑定有效、Profile 有效、实际 Scope 足够和任务请求合法；正式写入继续要求 ADR 0008 定义的单次确认。撤销某一绑定后，控制面立即拒绝该 `client_ref` 与 `profile_ref` 组合的新租约，但不撤销客户端证书、其他 Profile 绑定或 Profile 自身；已经交付到客户端内存的飞书短期令牌按其实际有效期和单独定义的应急策略处理。

## Considered Options

- 同租户内所有已登记客户端都可使用所有 Profile：拒绝，因为设备准入会被错误提升为全部用户委托，任一设备都可能冒用其他用户资源权限。
- 管理员登记客户端时自动绑定一个或全部 Profile：拒绝，因为管理员对设备的信任不能替代具体飞书用户对其个人授权的确认。
- 业务 Skill 在任务请求中传入任意 `profile_ref`：拒绝，因为调用方自报引用不能建立客户端与用户之间的授权关系，也会泄露 Profile 可枚举性。
- 每个客户端只能永久绑定一个 Profile：拒绝，因为共享工作设备或多个测试身份存在合理需求，但必须逐个绑定而不是隐式继承。

## Consequences

- 授权控制面必须持久化绑定的 `tenant_ref`、`client_ref`、`profile_ref`、批准用户主体、状态、创建时间、撤销时间和审计证据；绑定两端必须属于同一租户。
- 客户端只能查询自身绑定的最小 Profile 摘要和可用状态，不能取得同租户未绑定 Profile 的列表、主体详情或授权状态。
- 用户确认界面和单次请求合同遵循 ADR 0029，必须展示可辨认的客户端名称、`client_ref`、证书指纹摘要和请求绑定的 Profile，不能只显示笼统的“允许设备”。
- 客户端登记、Profile OAuth、客户端 Profile 绑定、Scope 增量授权和正式写入确认必须作为五种独立状态报告和审计。
- 绑定允许的语义能力遵循 ADR 0028；是否设定固定有效期以及已签发令牌的应急失效策略分别决策，不能由当前单机默认值隐式决定。

# 部分工作表写入只做前向恢复，不自动回滚

一次受管工作表交付由目标建立、值与公式、结构与样式、原生回读和 XLSX 导出验证等多个远端步骤组成，Feishu Sheets 没有覆盖整条流程的事务。任一步骤成功后，后续调用可能超时、返回不明或验证失败；此时自动删除新建工作表、清空已接管工作表或按本地预期反向覆盖，会扩大损失并可能抹去用户并发编辑和诊断证据。

Provider 因而在首次可证明的远端变更后立即把目标登记为临时受管状态，锁定原 Profile、工作簿、稳定工作表标识、操作标识和规范摘要。恢复只接受同一 Schema 版本且规范化摘要一致的工作表交付规范，先逐项语义回读已记录检查点，再跳过已经完成的步骤并继续尚未证明完成的确定性步骤。任何结果不明都先进入 ADR-0009 的恢复对账，不能把相同请求无条件重发。

Provider 不自动删除已新建工作表，不清空或还原已接管工作表，也不把失败切换到另一个工作表。用户若决定停止恢复，必须通过后续独立的显式放弃流程确认；放弃只关闭 Provider 的继续写入权并保留墓碑和目标可能不完整的警告，首个纵切不执行远端清理。只有 API 与导出双重语义回读全部通过后，临时状态才提升为已交付的受管工作表登记。

## Considered Options

- 新建模式失败就自动删除工作表：拒绝，因为删除可能移除用户在部分成功后添加的内容，也会销毁恢复证据。
- 接管模式失败就恢复写前快照：拒绝，因为写前快照不能原子隔离并发修改，反向覆盖会造成新的数据损失。
- 每次失败都从第一个步骤重新写：拒绝，因为远端请求缺少统一幂等键，重复新建、合并或覆盖的风险不可接受。
- 任何失败都永久禁止继续：拒绝，因为已经语义完成的步骤可以通过稳定标识和精确回读安全确认，确定性剩余步骤应允许受控恢复。

## Consequences

- 写入编排必须把每个远端步骤设计为可命名、可检查、可恢复的状态转换，并在步骤前后持久化检查点。
- 恢复工具不得接受新预览、新目标或不同规范；任何差异都要求先显式放弃旧操作，再从新的零副作用预览开始。
- UI、MCP 结果和诊断必须区分 `delivered`、`recovery_required`、`verification_incomplete` 与用户已放弃但远端仍可能含部分内容的状态。
- 首个纵切可以提供只读恢复诊断和同操作继续能力；远端删除或内容清空必须留给未来单独设计并再次确认。

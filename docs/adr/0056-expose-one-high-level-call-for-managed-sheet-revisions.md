# 受管工作表修订只公开一次高阶调用

受管工作表修订公开一个高阶工具调用，接收 `registration_ref`、稳定 `task_ref`、完整 `base_spec` 和 `next_spec`。该调用内部自动完成受管登记加载、规范归一化、严格无漂移核验、差异与退役区域计算、不可变操作登记、一次 MCP elicitation、写入、双重语义回读和最终登记前移；调用方不再手工编排修订专用的 `preview → apply` 两次工具调用。

合并公开调用不合并或删除内部安全阶段。Provider 仍必须在任何副作用前持久化与目标及规范对精确绑定的预览和幂等检查点；同一目标、任务和规范对的重试恢复同一不可变操作，不重复征求确认。只有新的规范对、新目标或已拒绝和取消后的新尝试才建立新的确认边界。首次交付现有的 `feishu_managed_sheet_preview` 与 `feishu_managed_sheet_apply` 暂时保持兼容，本 ADR 只收窄后续修订的调用体验。

## Considered Options

- 为修订再公开独立 preview 与 apply 工具：拒绝，因为调用方需要重复传递两份完整规范、保存操作引用并编排恢复，增加了操作复杂度但没有增加用户确认强度。
- 把修订作为现有首次交付工具的新增放置模式：拒绝，因为首次接管或新建目标与修订稳定登记对象具有不同前置条件，联合参数会形成难以理解的多态契约。
- 删除预览记录并在确认后直接写入：拒绝，因为这会失去精确规范绑定、短期授权、幂等恢复和进程退出后的审计能力。

## Consequences

- MCP Server 新增一个修订高阶工具；内部服务仍可拆分为预检、确认、执行和恢复组件进行测试。
- 用户每次新修订只看到一张确认卡片；内部技术检查、写后验证以及同一操作恢复不产生额外确认。
- 操作状态库必须以受管登记、任务、基线摘要和目标摘要识别同一修订请求，并阻止并发创建相互竞争的修订操作。
- 修订结果始终返回稳定 `registration_ref` 与审计用 `operation_ref`，但正常重试不要求用户或业务 Skill 手工传递操作引用。

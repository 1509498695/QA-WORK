# 对无变化受管工作表修订进行只读短路

当归一化后的 `base_spec` 与 `next_spec` 摘要完全相同时，一体化修订调用不得建立写入授权、展示 MCP 确认、产生远端副作用或追加受管版本。Provider 仍须加载同一受管登记并自动核验远端受管语义等于基线；核验完整时返回明确的 `status=no_change`、当前 `managed_version` 和读取证据，展示元数据变化可以安全刷新但不构成业务版本。

若远端语义已经偏离基线，即使两份调用规范相同，也必须返回 `precondition_failed` 并保持零写入。相同规范摘要只证明调用方没有提出目标变化，不能证明用户没有在远端人工修改受管内容。

## Considered Options

- 摘要相同即不读取远端并直接返回成功：拒绝，因为会掩盖人工漂移，让调用方误以为受管对象仍处于已验证状态。
- 为零差异请求建立普通修订版本并要求确认：拒绝，因为没有任何待授权的远端变化，只会制造无意义门禁和审计噪声。
- 把零差异返回为普通 `delivered`：拒绝，因为它没有执行交付，应与已经产生并验证远端副作用的结果区分。

## Consequences

- 公共操作状态增加 `no_change`，并继续提供完整读取证据和稳定登记引用。
- 零差异路径复用修订前基线核验，但不进入写入状态机或占用下一版本号。
- 业务 Skill 收到 `no_change` 时可以保持现有基线资产和 `revision_ready=true`，无需重写资产。
- 展示字段刷新必须与业务版本历史分离，不能伪造一个内容修订。

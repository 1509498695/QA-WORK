# 受管工作表修订必须由调用方同时提交基线规范和目标规范

受管工作表的后续修订采用严格无漂移前置条件：调用方在修订预览中同时提交完整的 `base_spec` 与 `next_spec`。Provider 必须先归一化 `base_spec`，证明其摘要等于受管工作表登记中的最近交付规范摘要，再完整回读同一远端工作表并证明其受管语义仍等于 `base_spec`；任一检查失败都在预览阶段关闭，且不得产生远端写入。只有基线一致时，Provider 才能为 `next_spec` 建立与这对规范精确绑定的确认预览。

Provider 的操作状态库继续只持久化规范摘要、稳定目标、操作状态和验证证据，不持久化工作表业务正文。保留或重建上一版完整规范是调用方责任；远端当前内容不能反向充当修订基线，因为那会把未经确认的人工修改误认为合法状态。

## Considered Options

- 由 Provider 长期保存每一版完整规范：拒绝，因为这会把最小技术状态库扩大为业务正文仓库，增加隐私、生命周期和迁移责任。
- 只提交 `next_spec`，由 Provider 根据登记摘要或远端现状推断基线：拒绝，因为摘要无法单独完成语义比较，而远端现状可能已经发生人工漂移。
- 检测漂移后自动合并或静默覆盖：拒绝，因为 Provider 无法推断人工改动与生成规范之间的业务优先级；编辑权限也不等于覆盖这些改动的授权。

## Consequences

- 修订预览的公开输入和预览身份必须同时绑定基线规范摘要与目标规范摘要。
- 基线缺失、基线摘要不匹配、远端读取不完整或任一受管语义漂移都必须以可诊断冲突结束，并保持远端零写入。
- 调用方需要可靠保存或确定性重建最近一次已交付的完整规范；Provider 只登记足以认证它的摘要。
- 修订成功并完成同一对象语义验证后，受管登记中的最近交付规范摘要才可前移到 `next_spec`。

# 中央控制面采用三角色权限模型

中央授权控制面只向用户暴露普通成员、团队管理员和平台管理员三种权限，不设置平台所有者或永久团队所有者。普通成员使用平台已开放的业务能力；团队管理员管理本团队成员、邀请和展示资料；平台管理员维护控制面、Provider 部署绑定、平台管理员名单和跨团队管理恢复。平台管理权不授予团队业务内容访问，也不绕过用户自己的 Feishu OAuth、资源权限或正式写入确认。

首位部署者必须通过服务端一次性 Bootstrap 和飞书 OAuth 成为第一名平台管理员。平台管理员可以有多名；人员交接采用“添加接手人、接手人接受并验证、移除原管理员”，系统禁止移除最后一名有效平台管理员。团队管理员同样可以有多名且至少保留一名。团队失去有效管理员时，平台管理员可以在重新验证身份、说明原因并记录审计后，把该团队的现有成员提升为团队管理员。

平台配置、管理员增删和团队恢复等高风险动作要求当前操作者近期重新验证身份、进行一次明确确认并保留审计；首版不要求第二名管理员重复批准。服务器侧紧急恢复仍是独立运维能力，不通过公共页面把普通用户提升为管理员。

## Considered Options

- 唯一平台所有者加多名平台管理员：拒绝，因为所有权转让、接手人接受、双人恢复和特殊退出规则形成额外状态机，却没有增加内部单租户首版所需的日常价值。
- 只保留普通用户和平台管理员：拒绝，因为成员邀请、团队资料和日常人员变更都会集中到平台管理员，形成不必要的运维瓶颈。
- 使用共享平台管理员账号：拒绝，因为无法证明操作者身份，也无法安全撤销单个人员或形成可信审计。
- 为每个管理动作建立独立细粒度角色：拒绝，因为首版团队规模和风险尚不足以支持复杂策略引擎，用户也难以理解实际权限。

## Consequences

- UI 只按当前身份显示“团队与账号”“团队管理”“平台设置”三个入口，不要求用户首次使用时自选角色。
- 数据模型分别保存平台管理员资格和当前唯一团队中的成员或团队管理员资格；一个人可以是平台管理员，同时在自己的团队中是普通成员或团队管理员。
- 管理员交接不再存在平台所有权迁移；最后一名平台管理员和最后一名团队管理员由服务端不变量保护。
- 高风险管理动作依赖近期身份验证、一次确认和审计，而不是默认双人审批；未来出现合规要求时再以新 ADR 增加审批策略。
- 飞书开发者后台应用管理员仍属于外部管理链，中央门户内的角色变更不能替代其交接。

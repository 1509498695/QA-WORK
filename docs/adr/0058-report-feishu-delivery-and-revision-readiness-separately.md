# 分别报告飞书交付完成和后续修订就绪

Feishu Provider 已完成写入及同一对象双重语义验证时，本次远端结果就是 `status=delivered`。业务 Skill 随后把同一 `next_spec` 保存为调用方修订基线；该本地持久化形成独立的 `revision_ready` 状态，不能反向改变已经证实的远端交付事实。若保存失败，整体结果必须同时报告 `status=delivered`、`revision_ready=false` 和稳定诊断 `baseline_persistence_incomplete`。

对基线持久化的恢复只允许重试调用方本地资产写入，并复用当前任务仍持有且摘要匹配的 `next_spec`。它不再次调用飞书写入、不建立新远端操作，也不重复 MCP 确认。保存成功后可以把 `revision_ready` 前移为 `true`；若任务结束前仍未恢复，必须明确说明当前远端交付有效，但将来的修订会因 `base_spec_required` 失败关闭。

## Considered Options

- 把本地基线保存失败统一报告为交付失败：拒绝，因为这会掩盖远端已经改变且验证完成的事实，并可能诱发危险的重复写入。
- 在基线未保存时仍报告完整成功：拒绝，因为用户会错误认为该受管对象可以继续无缝修订。
- 自动回滚已经交付的飞书内容：拒绝，因为本地审计资产失败不授权第二次远端破坏性操作，而且回滚本身可能失败或覆盖并发变化。

## Consequences

- 业务 Skill 的最终结果需要并列携带 Provider 交付状态与调用方修订就绪状态，不能压缩成单一成功布尔值。
- 基线保存应先在临时位置完成校验再原子替换；失败重试必须证明规范摘要仍等于本次已交付摘要。
- 用户不需要为本地恢复再次确认，但必须在恢复最终失败时收到明确、可操作且不误导的状态说明。
- Provider 状态库不承担调用方资产失败的修复责任；其 `delivered` 证据和最新受管登记仍保持权威。

# 集中托管飞书长期凭证但不代理业务内容

Feishu Provider 单独建设飞书授权控制面，集中处理 OAuth 发起、回调、一次性 `state` 校验、授权码交换、Scope 增量授权、Token 刷新与撤销，并加密保存专用应用 App Secret 和各用户 Profile 的 Refresh Token。该控制面属于 Feishu Provider，不属于业务 Workspace，也不是 ADR 0021 拒绝的中央 Broker MCP；它不得接收、读取或代理 Docx、Wiki、Sheets、图片、附件、任务快照和正式交付载荷。

Provider 执行客户端必须先向授权控制面证明自身身份，并具有 ADR 0027 定义的有效客户端 Profile 绑定，才能按 ADR 0030 为确定任务、用户 Profile 和语义能力请求短期访问令牌租约。控制面依据飞书实际返回的有效期交付 User Access Token；执行客户端只在当前任务的进程内存中持有它，并直接调用飞书受控语义 API，不写入磁盘、任务产物、日志或 MCP 正文。长期凭证不下发到执行客户端，App Secret 不分发到本机。OAuth 能力授权和客户端 Profile 绑定都不构成任何一次正式写入授权。

首版只登记一个本机执行客户端，但控制面身份模型从首版就区分租户、用户主体、执行客户端和 Provider Profile；后续多人、多设备接入通过增加登记和隔离实例扩展，不把单机默认值提升为共享身份。控制面按 ADR 0024 从首版独立部署，并按 ADR 0025 首阶段只允许一个飞书企业租户；执行客户端按 ADR 0026 使用独立证书和 mTLS 完成认证。具体托管平台、密钥管理产品和高可用方案分别决策。

## Considered Options

- 中央服务代理所有飞书读取和写入：拒绝，因为业务内容会汇聚到中央服务，并重新形成跨业务数据面和单点 Broker。
- 将 Refresh Token 返回本机保存：拒绝，因为多人使用时每台设备都会成为长期凭证库，统一撤销、轮换和租户隔离难以证明。
- 将 App Secret 分发给所有本机 Provider：拒绝，因为共享应用密钥会扩散到每个客户端，泄漏后无法区分或隔离单台设备。
- 中央服务只接收回调并把授权码转交本机：拒绝，因为本机仍需要 App Secret 完成交换和刷新，不能实现专用应用凭证集中托管。

## Consequences

- 飞书授权控制面成为高敏感凭证系统，必须具备传输加密、静态加密、密钥隔离、租户隔离、最小权限、审计、重放防护和撤销能力。
- 控制面不可用时不得回退本机 App Secret 或 Refresh Token，也不得把 ADR 0030 的旧任务租约用于新任务；已签发的当前任务短期令牌只可按 ADR 0031 在最长十分钟的平台租约内继续使用。
- 本机系统凭证库只保存 ADR 0026 定义的当前执行客户端私钥和证书，不保存飞书 App Secret 或 Refresh Token。
- 授权控制面的健康、客户端认证、客户端 Profile 绑定、Profile 授权和具体任务预检必须分别报告，任一层就绪不能替代其他层。
- 客户端、绑定和 Profile 凭证异常按 ADR 0032 分为普通对象撤销与紧急 Profile 隔离；首个纵切只实现手动、可回读、可审计入口。

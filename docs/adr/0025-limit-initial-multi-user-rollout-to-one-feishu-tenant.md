# 首阶段多人使用限定在一个飞书企业租户

Feishu Provider 的首版和第一阶段多人使用只允许一个经过显式租户准入的飞书企业租户；该租户内可以登记多个用户 Profile 和多个 Provider 执行客户端。授权控制面必须从飞书返回并验证的用户主体中确定租户身份，不能接受客户端、链接或业务 Skill 自报的租户值；不属于准入租户的 OAuth 结果不得建立 Profile 或保存长期凭证。

虽然运行策略只开放一个租户，数据合同从首版就在 Profile、用户主体、客户端授权、Token、审计和受管对象登记中保留稳定 `tenant_ref`，所有唯一性和访问判断都包含租户边界。单租户默认值不得省略、写死为空或被当作全局共享空间。

跨企业租户支持不是简单增加允许列表。按照飞书企业自建应用的使用边界，未来若要让其他企业安装和使用，需要单独决定商店应用或其他合规应用模式、租户管理员安装授权、每租户 Scope、数据隔离、密钥与运维责任，并以新 ADR 和迁移验收启用；在此之前跨租户默认关闭。

## Considered Options

- 首版即允许任意飞书企业用户自助 OAuth：拒绝，因为企业自建应用、数据隔离和管理员授权边界尚未建立，也会把未审阅租户写入长期凭证库。
- 数据库按单租户省略租户字段，跨租户时再迁移：拒绝，因为 Profile、审计、受管对象和唯一键都会形成全局身份，后续迁移容易造成越权关联。
- 为每个新企业复制一套相同服务和数据库：拒绝，因为应用身份、版本、安全修复和审计策略会分叉，且尚未证明这是目标运营模型。

## Consequences

- 首阶段“多人”明确表示同一飞书企业内的多个用户或设备，不表示多个企业租户。
- OAuth 成功但租户不匹配时返回 `tenant_not_allowed`，并保持零 Profile 创建、零长期凭证持久化和零业务调用。
- 所有缓存键、审计查询、Profile 查找和受管对象引用都必须包含 `tenant_ref`，即使当前只有一个允许值。
- 跨租户需求出现时先重新评估飞书应用类型和合规流程，不得把本 ADR 的企业自建应用结论外推。

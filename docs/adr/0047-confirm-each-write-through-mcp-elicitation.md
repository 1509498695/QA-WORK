# 每次正式写入通过 MCP elicitation 确认

Feishu Provider 的首个本机写入纵切使用两个公开语义工具完成一次交付。写入预览工具只读取并校验目标、规范化工作表交付规范、形成不可变预览，并持久化不含业务正文的最小预览记录；记录绑定任务、Provider Profile、目标工作簿、工作表放置模式、确定工作表或拟建名称、远端前置状态、内容摘要、规范版本和失效时间。正式应用工具必须重新接收同一交付规范、重新计算摘要，并与预览记录逐项匹配。

正式应用工具在任何远端副作用之前通过 MCP elicitation 展示预览的目标、主体、动作、工作表、影响范围和内容摘要。只有当前 MCP 客户端返回 `accept`，且 Provider 再次验证目标前置状态仍匹配时，Provider 才在服务端建立绑定该预览的短期单次正式写入授权，并立即以同一幂等操作消费它。`decline`、`cancel`、超时、客户端未声明或不能完成 elicitation，以及字段或远端状态漂移都必须保持零写入并返回稳定状态。

调用方不得提交 `confirmed=true`、聊天文本、伪造确认结果或自建授权引用替代 MCP elicitation。业务 Skill 可以调用预览并发起正式应用，但不能代替用户接受确认。OAuth Scope、客户端 Profile 能力绑定和本次正式写入授权继续是三种独立状态。本 ADR 只规定 ADR-0044 的本机单用户开发纵切；正式多人部署仍需把用户、客户端和任务身份纳入可审计的生产边界。

## Considered Options

- 把普通聊天中的“确认”作为 Provider 参数：拒绝，因为 Provider 无法区分真实用户动作与调用方构造的字符串，也无法绑定 MCP 请求和不可变预览。
- 在正式应用参数中接受布尔确认：拒绝，因为任何工具调用方都能直接设置该字段，不能形成服务端单次授权。
- 每次正式写入跳转到独立浏览器页面：暂不采用，因为当前 MCP 客户端已提供与工具请求关联的 elicitation 通道；OAuth 和长期客户端 Profile 绑定仍保留浏览器身份流程。

## Consequences

- MCP Server 必须检测客户端 elicitation 能力并区分接受、拒绝、取消和不支持；不支持时不得降级到无确认写入。
- 预览引用必须高熵、短期、不可枚举且绑定最小持久记录；业务正文继续由调用方任务持有，正式应用时重新提交。
- 接受动作必须先形成服务端授权与幂等检查点，再开始任何新建 Sheet、写值、设样式或合并操作。
- 恢复对账属于原授权操作的只读延续，不再次弹出确认；任何新目标、新内容或新操作必须重新预览并确认。

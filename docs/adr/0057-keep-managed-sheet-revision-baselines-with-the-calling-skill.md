# 由调用方业务 Skill 持有工作表修订基线正文

受管工作表修订所需的最近一次完整交付规范由调用修订能力的业务 Skill 持有，而不是由 Feishu Provider 持久化。每次首次交付或修订完成后，调用方按稳定 `registration_ref` 与规范摘要保存规范化 JSON；下一次修订由 Skill 自动加载该资产作为 `base_spec`，同时把新生成状态作为 `next_spec` 提交给一体化修订工具。正常用户操作因此仍然只是提供目标链接和新内容并确认一次。

该 JSON 是调用方任务暂存区或审计包中的不可变规范资产，不是 XLSX、远端导出文件或用户交付物。Provider 的本机操作状态库继续只保存摘要、受保护目标、操作检查点和验证证据。若调用方找不到摘要匹配的基线资产，Provider 必须返回稳定的 `base_spec_required` 并保持零写入；不得把远端当前内容反向构造成已认证基线，因为那会接受可能未经本流程确认的人工改动。

## Considered Options

- 由用户手工保存并在每次修订时提交上一版 JSON：拒绝，因为 opaque 技术资产会直接增加用户操作负担并容易错配目标。
- 由 Provider 数据库保存完整最新规范：拒绝，因为这会推翻最小技术状态边界，使通用 Provider 成为跨业务正文仓库。
- 只保存摘要并从远端重建规范：拒绝，因为当前规范摘要绑定结构化输入表达，远端状态不能可靠重建同一规范，也不能证明其中没有未确认漂移。

## Consequences

- 每个支持受管修订的业务 Skill 都必须实现相同的基线资产接口、规范摘要校验和原子替换策略；通用 Provider 不猜测调用方文件布局。
- 调用方只在 Provider 返回 `delivered` 且同一对象验证完整后，才把 `next_spec` 提升为新的基线资产。
- 基线资产可以随业务审计包迁移或归档，但不能在仍需修订受管对象时被无提示清理。
- Provider 的公开失败合同需要增加 `base_spec_required`，用于区分缺少调用方正文与远端漂移、授权失败或目标不存在。

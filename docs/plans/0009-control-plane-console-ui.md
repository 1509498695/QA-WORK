# 中央控制面控制台 UI 设计

## 状态

2026-09-01 UI 设计与真实状态纵切已完成。`platform/control-plane` 已实现四个主路由、共享响应式样式、Feishu OAuth 身份交付、SQLite 平台状态、团队与三角色服务端授权；页面不再包含固定示例身份或团队。

## 产品对象与页面任务

本控制台服务于使用飞书策划来源生成并交付测试用例的内部 QA。页面的单一任务是让用户快速回答三个问题：我是谁、我属于哪个团队、我现在可以做什么。业务用例生成仍发生在 Codex 与业务 Skill 中，控制台不复制业务工作台。

## 已确认信息架构

控制台只有四个主页面：

| 主页面 | 建议路由 | 可见范围 | 单一职责 |
| --- | --- | --- | --- |
| 首次使用 | `/start` | 未登录、未加入团队或通过邀请进入的用户 | 完成飞书登录，并加入或创建一个团队 |
| 团队与账号 | `/account` | 所有已登录用户 | 查看身份、当前团队、客户端与业务就绪状态，并维护个人显示名称 |
| 团队管理 | `/team` | 当前团队的团队管理员 | 管理本团队资料、成员、邀请和团队管理员 |
| 平台设置 | `/platform` | 平台管理员 | 管理中央服务状态、Provider 配置、平台管理员和开发重置 |

Feishu Provider 配置属于“平台设置”的内部内容，不建立第五个顶级控制台页面。加入团队、创建团队和换队属于“首次使用”的状态分支，不各自建立菜单项。

以下是无导航流程状态，不计入主页面数量：

- `/bootstrap/local`：仅在本机启动进程持有一次性 Bootstrap 证明时发起首次平台管理员登录；证明不进入浏览器。
- `/bootstrap/{token}`：兼容终端生成的一次性 Bootstrap 链接，消费证明后进入首次平台管理员流程。
- `/auth/feishu/callback`：只处理 Provider 一次性身份票据并重定向到原流程。
- `/confirm/{action}`：展示绑定确定动作的一次高风险确认。
- `/result/{id}`：展示成功、失败或下一步，不形成可长期浏览的菜单页面。

## 已确认角色导航

| 当前资格 | 主导航 |
| --- | --- |
| 未就绪用户 | 首次使用 |
| 普通成员 | 团队与账号 |
| 团队管理员 | 团队与账号、团队管理 |
| 平台管理员 | 团队与账号、平台设置；只有同时担任本团队管理员时才显示团队管理 |

页面不展示灰色的无权限菜单，也不以角色名称堆叠多个控制台。直接访问无权限路由时返回明确的权限说明和可执行返回入口，不能依赖隐藏导航作为服务端授权。

## 已确认整体框架

- 使用紧凑顶部导航替换当前贯穿全高的深色左侧轨道，避免普通成员只有一个入口时仍被沉重导航占据空间。
- 主内容使用最大约 `1120px` 的居中工作区；标题只说明当前任务，不使用占据首屏的大型宣传句。
- 顶部固定展示真实就绪链“本机安装 → 中央服务 → 飞书登录 → 团队 → 业务能力”。它显示每一项的通过、待处理或阻塞状态，并把唯一主要修复动作放在第一个未通过节点。
- 桌面端使用顶栏加内容区；窄屏将主导航折叠为菜单，就绪链允许横向滚动或收束为当前阻塞项，不产生第二套移动端信息架构。
- OAuth、确认、结果和空状态沿用同一页面框架与术语，不切换到另一套“配置向导”视觉语言。

## 已确认首次使用页

首次使用页采用“先选择目标，后完成飞书 OAuth”的单页状态流程，不建立独立登录页。

### 默认入口

- 页面标题使用“你准备怎么开始？”，直接提供“加入已有团队”和“创建团队”两个动作。
- “加入已有团队”是内部 QA 的默认主要动作；“创建团队”保持清晰可见，但不与主要动作争夺同一视觉权重。
- 用户点击动作后，服务端只记录一个短期、不可用于授权的流程意向，再发起飞书 OAuth；OAuth 成功后回到原分支，选择本身不建立身份、团队或权限。
- OAuth 失败、取消或租户不匹配时回到原分支并显示具体修复动作，不把用户送回无上下文首页。

### 加入团队

- 用户从普通入口选择“加入已有团队”时，OAuth 完成后再输入邀请链接；服务端验证邀请的团队、租户、有效期、剩余次数和撤销状态后展示目标团队摘要。
- 用户直接打开邀请链接时，不再显示加入/创建选择，而是展示目标团队名称和“验证身份并加入”；完成 OAuth 后继续同一邀请。
- 已有团队的用户必须看到将离开的当前团队和将加入的新团队，并只确认一次原子换队；加入失败时仍留在原团队。

### 创建团队

- 用户选择“创建团队”并完成 OAuth 后进入团队名称与必要展示信息，不在登录前收集会被丢弃的业务表单。
- 未加入团队的用户创建成功后成为首位团队管理员；已有团队用户继续遵守同控制面创建或创建全新团队环境的既定规则。
- 创建成功后直接进入“团队与账号”，不再增加单独完成页；页面通过一次结果提示说明团队和权限已经建立。

### 页面骨架

```text
QA Skill Hub                                      帮助
本机安装 ─ 中央服务 ─ 飞书登录 ─ 团队 ─ 业务能力

你准备怎么开始？
选择目标后，我们再验证你的飞书身份。

加入已有团队  ───────────────────────────────→
使用团队管理员发给你的邀请链接

创建团队       ───────────────────────────────→
在当前中央服务中建立新的 QA 团队
```

两个动作使用纵向任务行而不是两张通用营销卡；整个首屏只出现一个问题，不同时展示账号表单、Provider 配置或角色说明。

## 已确认团队与账号页

“团队与账号”是所有已登录用户的默认状态首页，采用“就绪状态优先”，不设计成传统个人资料中心或数据仪表盘。

### 就绪结论

- 页面顶部直接显示“可以开始使用”或一个确定的当前阻塞项，不要求用户自行解释多张状态卡。
- 全局就绪链继续显示每个检查点，但页面只为第一个可处理阻塞项提供一个主要动作，例如“连接中央服务”“重新授权飞书”或“加入团队”。
- 所有检查通过时，结论使用“已可返回 Codex 生成用例”；首版不提供无法保证宿主支持的自定义 Codex 跳转按钮。
- 安装完成、中央服务可达、飞书登录、团队成员资格和业务能力继续分别判断；页面不能用笼统的“账号正常”掩盖其中某项失败。

### 账号与团队信息

- 身份分区展示飞书认证姓名与头像、用户显示名称和不可变 `user_ref` 短标识；只有用户显示名称可在此编辑。
- 团队分区展示当前团队名称、`team_ref`、本人在该团队内的资格和加入时间；平台管理员资格单独标注，不能混写成团队职位。
- 尚未加入团队时，团队分区只说明当前状态并提供进入首次使用页的主要动作，不展示空成员列表或虚构默认团队。
- Feishu 分区只展示已连接主体、最近一次验证状态和需要重新授权的原因；不展示 Access Token、Refresh Token、App Secret 或面向开发者的原始 Scope 列表。

### 次级操作

- 修改显示名称、重新 OAuth 和退出团队放在对应信息分区或一个清晰的次级菜单中，不与当前修复动作争夺主按钮。
- 退出团队前由服务端检查是否为最后一名团队管理员、是否存在未终结写入以及目标关系是否仍未变化；不满足条件时直接解释唯一下一步。
- 页面不展示业务次数、成员总数、授权天数或其他不能帮助当前用户完成任务的统计卡片。

### 页面骨架

```text
团队与账号                         陈镇 · QA 平台组
本机安装 ─ 中央服务 ─ 飞书登录 ─ 团队 ─ 业务能力

已可以开始使用
返回 Codex，提供策划文档和目标表格链接即可生成用例。

身份
飞书认证姓名       用户显示名称       user_ref

当前团队
团队名称           团队资格           team_ref

飞书连接
授权主体           最近验证           [重新授权]
```

信息分区使用对齐的定义行和细分隔线，不把每一组数据包进独立悬浮卡片。

## 已确认团队管理页

团队管理页采用“单页成员表 + 邀请抽屉”，不建立成员详情、邀请管理或角色管理子页面。

### 页面主体

- 页首显示团队名称、稳定 `team_ref` 和成员数量；“生成邀请链接”是页面唯一主按钮。
- 成员使用一张可搜索的紧凑表格，列为成员身份、团队备注、团队角色、加入时间、当前状态和行尾操作。
- 成员身份同时展示飞书认证姓名、用户显示名称和 `user_ref` 短标识；重名不能导致管理员选错目标。
- 修改团队备注、提升或降级团队管理员、移除成员均从目标行的操作菜单进入，并在原页面完成一次明确确认。
- 最后一名有效团队管理员的降级和移除动作由服务端拒绝；界面同步禁用并直接解释“请先指定另一名团队管理员”。

### 邀请抽屉

- 点击“生成邀请链接”后从右侧打开窄抽屉，只设置有效期和可使用次数；目标团队、准入租户和签发人由服务端确定并只读展示。
- 生成后在同一抽屉显示邀请链接、到期时间和剩余次数，并提供一个“复制邀请链接”主要动作。
- 当前有效邀请显示在成员表下方的紧凑列表中，可以复制或撤销；已使用完、过期和已撤销邀请默认收起，但审计记录继续保留。
- 关闭抽屉不改变成员表筛选和滚动位置；邀请失败时保留已填写的非敏感设置并给出唯一修复动作。

### 页面骨架

```text
团队管理                                      [生成邀请链接]
QA 平台组 · team_7H2K                         12 名成员

搜索成员…
成员身份              团队备注       角色          加入时间      状态    ···
陈镇 / chen-zhen       用例负责人     团队管理员    08-20         正常    ···
李明 / li-ming         客户端 QA      普通成员      08-27         正常    ···

有效邀请  2
7 天 · 剩余 3 次 · 王芳签发                    [复制] [撤销]
```

打开邀请抽屉时，成员表仍作为稳定背景保留上下文；抽屉不是第五个主页面。

## 已确认平台设置页

平台设置页采用“全局顶部导航 + 页面内局部设置导航 + 单一工作区”。局部导航只存在于 `/platform` 内容范围内，不恢复贯穿整站的全高侧栏，也不增加顶级页面数量。

### 页面内导航

- 局部设置项固定为“服务概览、Feishu Provider、平台管理员、开发重置”。默认进入服务概览，当前项具有明确选中状态。
- 每次只在右侧工作区显示一个设置项；切换时保留全局顶部导航与就绪链，用户始终知道自己仍在平台设置中。
- 当前设置项写入 URL 的稳定 `section` 状态，使刷新、返回和受控直达能够恢复位置；服务端仍对每次读取和写入独立验证平台管理员资格。
- 窄屏下局部导航转为顶部横向设置列表，不隐藏为另一套菜单，也不改变各设置项名称。

### 服务概览

- 展示中央服务地址、服务状态、运行版本、准入租户、持久状态模式和最近一次只读自检。
- 只为第一个异常项提供一个主要修复动作，不展示请求量、在线人数或其他开发阶段无决策价值的统计图。

### Feishu Provider

- 展示 Provider 名称、配置状态、App ID、准入租户、App Secret 已安全保存状态和固定授权回调；绝不回显 Secret 或密文。
- “检查或修改”进入同一工作区中的编辑状态，保存前展示绑定确定草案并确认一次；结果仍返回平台设置的 Feishu Provider 分区。
- 连接验证是独立只读动作，只报告身份、租户、回调和所需能力的结构化状态，不把配置存在等同于用户 OAuth 或业务就绪。

### 平台管理员

- 使用紧凑列表展示飞书认证姓名、显示名称、`user_ref`、加入时间和状态。
- “添加平台管理员”打开右侧抽屉；接手人完成飞书 OAuth、接受并验证可进入平台设置后才生效。
- 移除管理员在原列表行完成一次高风险确认；最后一名有效平台管理员不能被移除。

### 开发重置

- 独立放在局部导航最后并使用克制危险色，正文精确列出将删除的测试身份、团队、Token、审计和未完成操作。
- 重置要求近期飞书身份验证和一次绑定当前开发实例的明确确认；普通初始化、版本检测和错误恢复不能触发。
- 完成后返回一次性 Bootstrap 起点，不伪装成正常退出登录；本入口在进入真实多人试用前必须移除或由部署策略关闭。

### 页面骨架

```text

                    授权回调      https://…/auth/feishu/callback

```

平台设置继续使用定义行、列表和分区表单，不把四个设置项做成四张状态卡。

## 视觉方向

视觉主题是“QA 就绪证据”，不是通用 SaaS 仪表盘。唯一强调元素是顶部就绪链，其余区域保持安静、紧凑并以任务和证据为主。

团队管理方向图已于 2026-09-01 确认作为四个主页面的共同视觉基线：紧凑顶部导航、居中工作区、真实就绪链、表格或定义行优先、右侧抽屉承载短任务。生成式方向图只约束层级、密度、色彩和构图；其中可能出现的文字或列对齐误差不构成实现文案与数据 Schema。

2026-09-01 已通过“团队管理”高保真方向图确认该基线：紧凑顶部导航、横向就绪链、居中工作区、表格型主体和保持上下文的右侧抽屉统一用于后续页面。方向图用于确认构图、密度和层级，不是文案、字段或像素实现真源；其中任何生成式文字或列对齐偏差不得进入真实页面。

### 色彩

- `Ink #0B1220`：标题、顶栏和高对比文本。
- `Slate #526078`：说明、次级信息和结构线。
- `Canvas #F6F8FC`：页面背景。
- `Paper #FFFFFF`：表单与工作内容表面。
- `Feishu Blue #3370FF`：主要操作和当前节点。
- `Ready Teal #0F9F7F`：已通过状态；警告使用克制的 `Amber #C77A12`，不以整块红绿背景表达状态。

### 字体

- 页面标题：`Segoe UI Variable Display`、`Microsoft YaHei UI`，使用紧凑字距和明确层级。
- 正文与控件：`Segoe UI Variable Text`、`Microsoft YaHei UI`。
- `user_ref`、`team_ref`、版本和诊断码：`Cascadia Mono`、`Consolas`。

### 组件与动效

- 页面不堆叠通用数据卡片；身份、成员、Provider 和设置按真实对象使用列表、定义表与分区表单。
- 主按钮每个视图最多一个；次要动作使用文字按钮或菜单，高风险动作只在对应管理分区出现。
- 页面切换不使用装饰性动画；就绪检查完成时只允许一次短促状态推进，并遵守 `prefers-reduced-motion`。
- 所有交互具有可见键盘焦点；颜色之外同时使用文字和图形表达状态。

## 设计禁止项

- 不恢复当前大面积深色侧栏、超大口号和右侧长期空白的失衡构图。
- 不为每个角色建立一套独立首页，不让用户在“成员控制台”和“管理员控制台”之间切换。
- 不把 OAuth 成功、保存成功、邀请成功等一次性结果放进长期导航。
- 不展示与当前用户无关的 Provider Secret、其他团队或平台操作入口。
- 不用无业务含义的统计卡、渐变数字、装饰性步骤编号或英文眉题填充页面。

## UI 设计结论

四个主页面、角色导航、首次使用流程、状态首页、团队成员工作台、平台设置组织和共同视觉基线均已确认。视觉稿中的生成式文字不作为实现真源。

## 真实状态实现

- 独立 uv Workspace 包 `platform/control-plane` 与 `providers/feishu/auth-service` 保持源码、数据库和凭证边界。
- 实现 `/start`、`/account`、`/team`、`/platform` 四个主路由，以及 Bootstrap、OAuth 回调、邀请、原子换队、角色管理和开发重置等无导航流程。
- 平台 SQLite 保存稳定用户引用、展示属性、会话、唯一团队成员资格、团队/平台管理员、邀请和审计；不保存任何 Feishu OAuth Token。

# 同租户内部 QA 首次使用优化

## 状态

2026-09-01 设计讨论中。本文只记录已确认的新用户目标与体验边界，不把当前 `local-dev-v0` 表述为已具备多人能力。

## 目标用户

- 第一优先级是同一飞书企业租户内、希望通过飞书策划来源生成并交付测试用例的内部 QA。
- Feishu Provider 专用应用、应用凭证与服务由平台管理员统一维护；每位 QA 仍以自己的独立 Provider Profile 完成 OAuth，不共享用户 Token、资源可见性或授权状态。
- 仓库开发者不是普通首次使用流程的目标用户，Git、uv、Plugin 构建和测试说明继续留在开发文档。

## 已确认体验边界

- 首次使用不要求用户自报或持久化“角色”。产品使用“使用路径”调整界面与引导，但不以它授予权限。
- 默认使用路径是“生成测试用例”：用户最终只需提供飞书策划来源和目标表格定位符，并在正式写入时处理一次原生确认。
- 只有预检发现 Provider 尚未建立部署绑定时，才显示“请联系平台管理员”和显式平台配置入口。
- 普通用户 OAuth、管理员部署配置、客户端 Profile 能力绑定、OAuth Scope 与单次正式写入授权继续是彼此独立的状态。
- 首批内部 QA 的正式使用以中央授权控制面为前置：平台管理员统一维护稳定 HTTPS 服务、Provider 专用应用和应用凭证，普通成员不配置 App ID、App Secret，也不持续运行 localhost 授权服务。
- 中央授权控制面可以部署在企业内网，但必须具有团队成员可通过办公网络或 VPN 访问的稳定 HTTPS Origin、受信任证书、固定 OAuth 回调、持久存储和到飞书开放平台的出站连通性；`localhost` 仍只用于个人开发验证。
- 中央授权控制面应由独立服务身份运行并持有加密状态，不得把长期凭证的可解密性绑定到首位部署者的个人 Windows 账号。平台管理资格必须支持增加、撤销和受控交接，使人员变动不要求重建 Provider Profile 或重新创建服务。
- Provider MCP 仍在获准执行客户端中取得短期任务租约后直连飞书；中央授权控制面不接收、代理或持久化策划正文和工作表内容。

## 已确认权限划分

该权限模型的取舍与恢复边界见 [ADR 0065](../adr/0065-use-a-three-role-access-model.md)。

- 产品只向用户暴露三种权限：普通成员使用业务能力，团队管理员管理本团队，平台管理员维护中央服务、Provider 配置和跨团队管理恢复；不再设置平台所有者或永久团队所有者。
- 新平台实例的首次部署者只有在本机控制面持有服务端生成的一次性 Bootstrap 证明，并完成飞书 OAuth 后，才能成为第一名平台管理员；打开页面或点击登录入口本身不得自动取得管理权。
- 平台管理员可以有多名。交接只执行“添加接手人、接手人 OAuth 并接受、验证可进入平台设置、移除原管理员”，不执行所有权转让；系统禁止移除最后一名有效平台管理员。
- 一个团队可以有多名团队管理员且必须至少保留一名；团队创建者只是首位团队管理员。团队失去有效管理员时，任一平台管理员可以在重新验证身份、填写恢复原因并留下审计后，把该团队的现有成员提升为团队管理员。
- 平台管理员可以同时是其唯一团队中的普通成员或团队管理员，但平台管理权本身不授予任何团队业务内容访问，也不绕过该用户自己的 Feishu OAuth、资源权限或正式写入确认。
- 平台配置、管理员增删和团队恢复等高风险动作要求当前操作者重新验证飞书身份、确认一次并记录审计；首版不要求第二名管理员重复批准。
- 中央门户内的平台管理员资格不等于飞书开发者后台应用管理员资格，人员交接时必须分别核验两条管理链。

## 已确认身份建立

- 普通用户不创建平台用户名或密码；首次需要登录、加入团队、创建团队或接受管理邀请时，通过飞书 OAuth 自动建立平台身份。
- 中央控制面只在 OAuth 成功且租户准入校验通过后，按稳定 `tenant_ref + app_id + open_id` 查找或幂等创建内部 `user_ref`；`union_id` 可以作为辅助关联，姓名、头像、邮箱和手机号不得作为身份主键。
- 自动建立平台身份不自动产生团队成员资格、团队管理权或平台管理权；这些关系分别由邀请、团队创建、Bootstrap 或管理员授予建立。
- OAuth 失败、租户不匹配或身份响应不完整时保持零用户创建、零团队关系和零长期凭证持久化。
- 平台分别保存飞书认证姓名、用户显示名称和团队备注：飞书认证姓名与头像由 OAuth 身份信息只读同步，用户可以修改自己的平台显示名称，团队管理员可以在本团队内维护成员备注。
- 显示名称允许重复且不参与登录、唯一性或授权判断；成员管理、平台管理、管理员交接和审计界面始终同时展示飞书认证姓名与不可变 `user_ref` 短标识。
- 显示名称和团队备注的变更记录操作者、修改前后值与时间；重新 OAuth 可以刷新认证姓名和头像，但不得覆盖用户显示名称或产生第二个平台身份。

## 已确认客户端与入口边界

- 一个 Provider 执行客户端只绑定一个中央授权控制面实例，不提供同一客户端内的多控制面列表或环境切换器；团队与 Profile 选择始终限定在该控制面内部。
- 已连接用户创建团队时明确区分“在当前中央服务下创建团队”和“创建全新团队环境”：前者复用当前控制面且只建立团队管理权，后者进入新控制面部署、Bootstrap、Provider 配置和首个团队创建流程。
- “创建全新团队环境”复用当前本地客户端而不创建第二个 Workspace：系统先在独立暂存状态完成新控制面配置、OAuth、首个平台身份和团队建立，全部验证成功后才原子替换客户端控制面绑定并撤销旧控制面的 `client_ref`；任一步失败都继续使用原绑定。
- 客户端切换不删除旧控制面中的平台身份、团队成员关系、历史操作或审计记录，也不等同于退出旧团队；用户若要退出旧团队必须执行独立操作。
- 存在 `possibly_modified`、`recovery_required`、`verification_incomplete` 或其他未终结远端写入时禁止替换客户端绑定，必须先完成原操作对账，避免丢失恢复链。
- 普通首次使用入口使用中央服务的稳定 HTTPS 页面；Provider 预检或业务 Skill 发现客户端未绑定、用户未登录或无团队时，返回受信任同源的短期 `action_url`，由 Codex 展示“打开首次使用页面”操作或打开浏览器。
- 用户也可以从中央服务首页的“团队与账号”入口进入同一页面；本机首次启动页可直接发起由进程内一次性 Bootstrap 证明保护的飞书登录，证明不得进入浏览器，普通团队入口不得升级为平台配置入口。
- 首版不依赖未公开或未验证的 Codex 自定义深链协议；浏览器跳转、回调与结果轮询以普通 HTTPS URL 和明确状态为稳定合同。
- 中央控制台只设置“首次使用、团队与账号、团队管理、平台设置”四个主页面；OAuth 回调、Bootstrap、操作确认和结果反馈都是无导航流程状态。详细信息架构与视觉方案见 [控制台 UI 设计](./0009-control-plane-console-ui.md)。

## 已确认本机初始化与升级

本机安装收口为一个幂等的“一键初始化”入口，具体取舍见 [ADR 0066](../adr/0066-bootstrap-local-installation-through-one-idempotent-entrypoint.md)。

- 普通 QA 拉取仓库后只运行一个本机入口；入口自动检查并协调用户级 Provider Plugin、业务 Skill 发现入口、必要运行依赖和当前中央服务入口，成功时直接打开团队登录或业务就绪页面。
- 平台管理员负责发布已经完成同一提交内自检的仓库版本；初始化器只安装当前检出版本所声明的 Plugin 与 Skill，不主动执行 `git pull`，也不从未受控地址追逐“最新版本”。
- 首次安装、缺失项修复和已发布版本升级使用同一幂等流程。无变化时静默通过；能够安全修复的缺失或旧版本直接修复；遇到同名非受管目录、来源不可信或当前版本自检失败时停止，不覆盖用户文件。
- 用户主动运行初始化入口即授权它修改本机当前用户范围内的安装状态，不再为 Marketplace 登记、Plugin 安装和 Skill Junction 分别重复确认；流程不要求管理员权限，也不得修改其他系统用户的环境。
- 初始化成功必须执行一次只读能力声明和任务预检，区分“本机安装完成”“中央服务可达”“用户已登录”“已加入团队”和“业务能力可用”；只有最后一项通过才显示可以开始生成用例。
- 初始化器可以打开中央门户或返回可信 `action_url`，但不得代替飞书 OAuth、团队邀请、平台 Bootstrap、正式写入确认，也不得因安装成功自动授予任何角色。
- 中途失败时保留最后一个已验证可用版本；结果只显示一个主要修复操作，并附稳定错误码和可复制诊断摘要。普通成员不需要理解 Marketplace、Junction、Plugin 缓存或 MCP 生命周期。
- 版本来源继续使用仓库已有的 Plugin manifest、个人 Marketplace 与 Skill 目录，不新增重复的自定义 Workspace 清单。

## 已确认团队规则

- 同一中央控制面内，一个平台身份只能属于一个团队；产品不显示团队切换器。加入另一团队是一次明确换队，新关系成功后才结束旧关系，旧成员历史和审计继续保留。
- 团队管理员签发有有效期、次数限制且可撤销的邀请链接。用户完成飞书 OAuth 与租户校验后直接加入；已有团队时只额外确认一次换队，不重复提交管理员审批。
- 未加入团队的已验证用户可以直接创建团队并成为首位团队管理员。已有团队的用户只有在旧团队仍有其他成员和其他管理员时才能创建新团队并原子退出旧团队；单人团队不能再建同控制面团队，只能修改当前团队资料或创建全新中央服务环境。
- 活动团队名称在同一控制面内规范化唯一；团队名称和展示资料可以修改，但稳定 `team_ref`、成员历史、受管对象和审计链不变。
- 团队管理员可以提升或降级本团队管理员，但系统始终保护最后一名有效团队管理员；无需把该约束表现为新的用户角色或日常审批流。
- 邀请、换队和创建团队在服务端保持原子性：任一校验或写入失败都维持原团队关系。存在未终结飞书写入或恢复状态时，系统仅在必要时阻止换队并给出恢复入口。
- 团队只能使用平台预设能力，团队管理员不能修改中央服务、Provider Secret、平台管理员或其他团队。
- “一人一团队”只在单个中央控制面内部强制；独立控制面不共享成员数据库或建立跨控制面全局身份。

## 已确认开发阶段边界

- 项目仍处于开发阶段，本阶段不建设跨主机状态迁移、旧 Schema 升级、旧本机 DPAPI 状态导入或灾备恢复兼容；实现可以通过显式开发重置建立新的干净状态。
- 开发重置后允许重新执行 Bootstrap、Provider 配置、飞书 OAuth、团队创建和客户端登记，不承诺保留此前的测试用户、团队、Token、审计或未完成操作。
- “平台管理员交接”仍指同一正在运行的中央服务内增加和移除管理员，不等于把服务及其数据迁移到另一台机器。
- 重置只允许通过明确标记的开发入口执行，不能由普通业务任务、版本检测或初始化失败静默触发；不保留兼容性不等于允许导出明文 Secret 或绕过安全边界。
- 一旦进入真实多人试用或需要保留真实授权状态，本开发边界立即失效；届时必须先单独设计并验收备份、恢复、Schema 迁移和跨主机接手，再声明可保存生产状态。

## 当前差距

- 当前实现仍是 Windows 当前用户边界内的 `local-dev-v0`，使用 localhost、DPAPI 和本机单用户 Profile；它不能作为内部多人上线证明。
- 当前 DPAPI CurrentUser 凭证边界不能证明其他平台管理员可以在同一中央服务内接手配置；中央部署还缺少独立服务身份密钥托管和管理员交接验证。
- 当前安装仍由个人 Skill Junction 脚本、Marketplace 命令、Plugin 重载和本机服务步骤分别完成，尚未实现上述统一初始化入口、原子升级与首次成功验证。
- 正式同租户多人使用仍依赖 ADR 0024～0029 定义的稳定 HTTPS 授权控制面、执行客户端身份、Profile 能力绑定、审计与撤销边界。
